## Documented contradiction between the lock/audit doc and the actual repository — and the correction applied

`docs/plans/audit/RESEARCH_LIFECYCLE_RECONNECTION_AUDIT.md` (the source document `IMPLEMENTATION_SEQUENCE_LOCK.md` cites for MR-1) asserts that `SelectResearchOpportunities` **"already unions arbitrary opportunity rows for a run"** and only needs a producer wired in.

Code evidence that this is false, as it stood before this slice
(`src/research_os/application/select_research_opportunities.py`, pre-Slice-3):

```python
generated = propose_diagnostic_opportunities(
    command.research_run_id,
    DiagnosticOpportunitySources(...),
    id_prefix=new_opaque_id(),
)
decisions = select_research_opportunities(
    generated,
    research_run_id=command.research_run_id,
    budget=command.budget,
    negative_knowledge=tuple(negatives),
    previously_selected_identities=previously,
)
```

`select_research_opportunities()`'s **only** input was `generated` — opportunities freshly synthesized in-process from `DiagnosticOpportunitySources` (differential/invariant/chain/change-event/hypothesis ids read from the ledger). The **only** read of the persisted `research_opportunities` table was `previously = frozenset(item.structural_identity for item in uow.research_opportunities.list_for_research_run(...))`, used exclusively as a **dedup set of already-selected identities**, never as a source of additional candidate opportunities to select from. There was no code path by which a Hunter-, Coverage-, or any other externally-produced opportunity could ever reach this selector. The audit doc's claim was incorrect; repository evidence overrides it per the user's explicit instruction, without weakening any MR-1 invariant.

### Corrected design (approved by the user before implementation)

Equivalent to "Option A" from the pre-implementation review: a small, additive **opportunity-selection/candidate** table bridges non-diagnostic producers into the existing selector, instead of (a) mutating `select_research_opportunities()`'s pure decision logic, or (b) adding mutable workflow/status semantics onto the existing `research_opportunity` table.

- `research_opportunity` remains the sole canonical `ResearchOpportunity` representation. Nothing about its schema, its meaning, or who writes to it (still only `SelectResearchOpportunities`, on a `SELECT` decision) changed.
- New table `opportunity_selection_candidate` is **only** a durable pre-admission proposal/bridge, not a second `ResearchOpportunity` authority and not a second lifecycle: it has exactly one state transition, `PENDING → {ADMITTED, NOT_ADMITTED}`, decided exclusively by `SelectResearchOpportunities` itself (never by the producer, never by any other code).
- Deliberately **not** named/reused in a way that conflicts with the existing epistemic `Candidate` concept (`Evidence → Candidate → Verification → FindingProposal → Finding`, defined in `src/research_os/data/records.py`'s `CandidateRecord` and this repository's own rules doc). Chosen name: `OpportunitySelectionCandidateRecord` / table `opportunity_selection_candidate` — explicit about being an opportunity-selection candidate, not a security-finding Candidate.
- `AutonomousResearchController` (ARC) is unchanged and remains the single next-action owner and the only caller of `SelectResearchOpportunities`; it is unaware the new table exists. No second scheduler, no second Worker-dispatch path.
- The pure decision function `select_research_opportunities()` in `src/research_os/research/exploration.py` is **not modified at all** — same signature, same admission/dedup/precedence/budget logic. Only its caller's input tuple grew (diagnostics ⊕ pending candidates).
- The producer (`HunterCoverageOpportunitySource`) is isolated: it has its own file, its own command/result types, and touches only `research_run`, `research_opportunity` (read-only, for cross-producer dedup), and the new table. It never writes `Hypothesis`, `Experiment`, `ExecutionAttempt`, `Evidence`, or `Candidate` state, and never calls `WorkerPort`.

## What changed

Producer (new, isolated):

- `src/research_os/application/hunter_coverage_opportunity_source.py` (new) — `HunterCoverageOpportunitySource`. Consumes an **already-computed** `tuple[ScoredCell, ...]` (e.g. `RunHuntSchedulerResult.recommended`, which itself wraps `compute_coverage_debt()` + `schedule_cells()`; neither is called again here, so this producer cannot drift from or duplicate that decision logic). For each cell whose `CoverageState` is `UNTESTED` or `HYPOTHESIZED` (cells already `V1_PASSED`/`V2_PASSED`/`V3_QUEUED`/`COVERED`/`NOT_APPLICABLE` have their own existing follow-up path — V1–V3 tier progression in `RunHuntCycle`, or a `HYPOTHESIS_FOLLOWUP` diagnostic opportunity once assessed — and are explicitly skipped here to avoid a second path for the same work), builds one deterministic `OpportunitySelectionCandidateRecord` (dimensions are ordinal, never a raw `HunterScore`/priority number, matching the existing "not a priority score" invariant in `research.exploration`) and inserts it if its `structural_identity` is not already present as a candidate or a canonical opportunity for that run (own dedup, so a coverage gap that persists across cycles is proposed exactly once, not once per cycle). Proposing a candidate never mutates coverage state itself — coverage is still reduced only by executed/admitted research results, exactly as required.

Selector (existing use case, minimal additive read-side change):

- `src/research_os/application/select_research_opportunities.py` — `SelectResearchOpportunities.execute()` now also loads still-`PENDING` `opportunity_selection_candidate` rows for the run, converts each into the same domain `ResearchOpportunity` value object diagnostics use (`_opportunity_from_candidate`, using the candidate's own `candidate_id` as a stable `opportunity_id`), and passes `generated + candidate_opportunities` into the **unmodified** `select_research_opportunities()`. ## MR-1 re-qualification: second-scheduler remediation (`RunResearchSelection`)

### Why Slice 3 was re-opened

The initial completion pass above (still accurate for the producer/selector/candidate-table work) explicitly flagged, in "Unresolved / explicitly out of scope," that `RunResearchSelection` was a **second, independent selection loop** with its own `ResearchOrchestrationRecord` mutation. The operator correctly identified that this directly contradicts MR-1's own PASS invariant — **single next-action owner** — regardless of whether Hunter/Coverage opportunities reach `SelectResearchOpportunities`. A unified opportunity *source* feeding two independent *schedulers* is not a unified lifecycle. Slice 3 was re-opened; Slice 4 was explicitly held back until this was resolved.

### Exact call-graph audit (before remediation)

- `AutonomousResearchController.step()` (`src/research_os/application/autonomous_research_controller.py`) is one owner: it alone reads/writes `research_orchestration` via `_complete_cycle`/`_checkpoint`/`_mark_running`, and it alone calls `SelectResearchOpportunities.execute()` for diagnostic+candidate opportunities, `ProposeResearchHypothesis`, `PreparePlannedExperiment`, and `ExecutePlannedExperiment`.
- `RunResearchSelection` (`src/research_os/application/run_research_selection.py`, pre-remediation) was a **second, structurally identical owner**: its `start()`/`step()`/`resume()`/`run_bounded()` methods read and wrote `uow.research_orchestrations` directly (`uow.research_orchestrations.insert(...)` / `.save(...)`), maintained its own `cycle_number`/`current_phase`/terminal-state semantics independent of ARC's, and drove its own deterministic HTTP object-authorization/state-transition probing loop (`research.selection.propose_experiment_options`/`select_next_experiment`) straight into `PreparePlannedExperiment`/`ExecutePlannedExperiment` — the same `ExecutePlannedExperiment` capability ARC uses, but reached through a second, independently-instantiated code path.
- **Caller graph**: grepped across `src/` and `tests/` — the only caller of `RunResearchSelection` anywhere in the repository was `tests/e2e/gate17_harness.py` (a test harness). No production wiring (CLI, API, scheduler, ARC) ever constructed or called it. This meant the "second scheduler" was live in the class hierarchy and covered by 57 e2e tests, but not reachable from any operator-facing entry point — good news for blast radius, but it still had to be resolved as an architectural class-level violation, not merely a dead-code cleanup, because MR-1's invariant is about the *design*, not just current wiring.
- Both paths ultimately called the *same* `ExecutePlannedExperiment`/`WorkerPort` instance when constructed together in a real process (there was never a second Worker adapter), so the risk was specifically **duplicate/conflicting `research_orchestration` ownership and progression logic**, not a second Worker integration.

### Remediation: delegation seam, not a second scheduler

Chosen approach: turn `RunResearchSelection` into a thin compatibility/delegation layer over `AutonomousResearchController`, per the operator's explicit preference, rather than deleting its deterministic HTTP-probing capability (which ARC's model-driven `ProposeResearchHypothesis`/`plan_admitted_hypothesis` path cannot currently express — it is limited to the diagnostic-echo plan shape, and `HypothesisProposal` has no field for `RunResearchSelection`'s authorization-differential/state-transition plan arguments; teaching ARC's model-driven path that capability is Slice 4/MR-2+ scope, not this remediation).

1. **New delegation seam on ARC** (`AutonomousResearchController.run_managed_cycle()`, `src/research_os/application/autonomous_research_controller.py`): accepts a caller-supplied `ManagedCycleFn` — `(current_record, self._prepare, self._execute, self._evaluate) -> ManagedCycleOutcome` — and always finishes by calling ARC's own `_complete_cycle()` with the returned outcome. This means:
   - ARC remains the **only** writer of `research_orchestration` (terminal-state guard, lease/fencing, cycle-number bookkeeping, `ResearchCycleRecord` insertion — all unchanged, all still exercised).
   - The caller's decision function only ever receives ARC's *own* single `PreparePlannedExperiment`/`ExecutePlannedExperiment`/`EvaluateExperimentFeedback` instances — the same ones `step()` itself uses — so there is exactly one Worker-dispatch code path in the process regardless of which strategy (model-driven or deterministic-HTTP) decided to use it.
   - `_complete_cycle()` was extended (not replaced) to accept a raw `str` for `stop_reason` (in addition to the existing `StopReason` enum) and a `_UNSET` sentinel for `pause_reason`, so `RunResearchSelection`'s own `ResearchStopReason` vocabulary and "leave pause_reason untouched vs. explicitly clear it" semantics pass through unchanged. No existing `_complete_cycle` caller's behavior changed (all existing positional/keyword defaults preserved).
2. **`RunResearchSelection` rewritten as a delegation layer** (`src/research_os/application/run_research_selection.py`): `start()`, `step()`, `resume()`, and `run_bounded()` now all delegate orchestration-record ownership to an internally held `AutonomousResearchController` (constructed with a `_NeverInvokedModelPort` — a `ModelPort` that raises if `.complete()` is ever called, satisfying ARC's constructor without ever enabling the model-driven path, since this consumer's contract is that the model is never invoked). `step()`'s original decision logic (portfolio construction, `propose_experiment_options`, `select_next_experiment`, negative-context/executed-identity bookkeeping, persistence of the resulting Hypothesis/Experiment/Opportunity/Selection rows) is preserved **verbatim as a private method** (`_run_selection_cycle`) and passed to `arc.run_managed_cycle()` as the `ManagedCycleFn`. `RunResearchSelection` no longer contains any call to `uow.research_orchestrations.insert`/`.save` — grep-verified (`grep -n "research_orchestrations\." src/research_os/application/run_research_selection.py` returns exactly one match, a read-only `uow.research_orchestrations.get(...)` in `start()` used only to decide whether to pre-seed the initial HTTP-authorization/state-transition hypotheses before delegating to `self._arc.start(...)` — every write to the orchestration record itself now happens exclusively inside `AutonomousResearchController`).
3. **No capability deleted**: the deterministic HTTP object-authorization/state-transition probing policy, its audit events (`RESEARCH_SELECTION_STARTED`, `RESEARCH_SELECTION_CYCLE`, carried through `ManagedCycleOutcome.extra_audit_events`), its bounded stop reasons, and its portfolio/negative-context tracking are all unchanged in behavior — proven by all 57 pre-existing `tests/e2e/test_gate17_autonomous_research_selection.py` tests (the only consumer) passing unmodified, with no test file changes beyond the earlier, unrelated Alembic-head bump.

### Result: exactly one next-action owner

After remediation, `AutonomousResearchController` is the **only** class in the repository that reads or writes `research_orchestration`. `RunResearchSelection` holds no independent orchestration state of its own; it is a policy plugin that ARC executes through `run_managed_cycle()`, exactly as `step()` itself is a (model-driven) policy that ARC executes through its own internal logic. There is exactly one component that decides "what happens to this `ResearchRun`'s orchestration record next": ARC.
